# Модель данных — этап 4, версия 0.7.0

Room 5 сохраняет UUID и числовые ключи существующих записей; JSON 2 переносит новые поля. Расширенные формы относятся к этапам 5–6. Этот документ описывает реализованные правила хранения и API репозитория.

## Каталог и состав

`NutritionRepository.foodCatalog.save` создаёт новую идентичность при `id = null`, даже при одинаковом названии. Редактирование сохраняет UUID, увеличивает `revision` и не меняет вид записи. Базовый продукт и вариант различаются `productKind`, маркой и уточнением. Уникальный индекс по названию снят; индекс UUID остаётся уникальным.

`saveCatalogEntry` — совместимый вход простой формы. Он повторно использует единственное совпадение базовой записи без марки и уточнения; неоднозначность требует выбора. При редактировании сохраняет метаданные, вложенный состав продукта и уже известные количества компонентов. Изменение набора компонентов подтверждённого блюда снимает подтверждение источника: состав становится частичным до новой проверки.

Категории имеют фиксированные коды: `grains`, `bread`, `vegetables`, `fruit`, `meat`, `prepared`, `fish`, `eggs`, `dairy`, `legumes`, `nuts`, `oils`, `seasoning`, `drinks`, `other`. Старое неизвестное значение — `null`. Полное наполнение и фильтры добавляются на этапе 5.

Блюдо ссылается на продукты через `dish_products`; продукт — на продукты через `product_components`. Связь содержит порядок и необязательное количество. Граф не допускает отсутствующих компонентов, прямых/косвенных циклов, глубины свыше 16 и развёртывания свыше 10 000 узлов. Повтор через разные ветви допускается; прямой повтор компонента у одного владельца запрещён. Сохранение проверяется до изменения графа и применяется транзакционно.

Статусы состава: `unknown`, `partial`, `confirmed`. Подтверждённый состав требует источника и даты проверки. Отдельные листовые продукты также имеют явный статус; название не доказывает наличие лактозы или отсутствие добавок. Неизвестный состав не трактуется как пустой подтверждённый состав. Метки веществ не выводятся автоматически.

`Portion` принимает пару положительное десятичное количество/единица (`g`, `ml`, `piece`) либо два `null`. До 18 целых и 6 дробных цифр, без экспоненциальной записи; API приводит строку к канонической форме. Количество не агрегируется между разными единицами; неизвестность не превращается в ноль. Дозировка лекарства дополнительно сохраняет прежний свободный текст.

## История

`saveMeal` допускает одно блюдо, один продукт или смешанный список. `id = null` всегда создаёт новое событие, включая повторный завтрак/обед/ужин за дату; изменение требует конкретного `id`.

Новая позиция сохраняет `sourceRevision` и самостоятельное JSON-дерево `compositionSnapshot`. Каждый узел содержит исходный UUID, имя, вид, версию, метаданные состава, количество связи и дочерние компоненты. Поэтому путь «котлета → фарш → чеснок» сохраняется после изменения или архивирования справочника. Плоский список ингредиентов остаётся для текущего отображения и анализа, исключает повторы и проверяется на соответствие дереву при импорте.

Обычное редактирование события сохраняет UUID позиций, снимки, порции и комментарии. Параметр `refreshComposition` явно обновляет только указанные позиции; их UUID, порции и комментарии сохраняются. Пользовательская форма просмотра/подтверждения такого обновления относится к этапу 5; сейчас простой интерфейс обновляет рецепт через новое событие. Параметры `portions`/`comments` изменяют только явно переданные позиции; явные пустые значения очищают поле.

Все снимки одного приёма вместе ограничены 10 000 узлами. Старые плоские ингредиенты и свободные описания не превращаются в выдуманное дерево: `sourceRevision`/`compositionSnapshot` остаются `null`.

## Время, сон и полнота

`EventContext` задаёт необязательные фактическое время и комментарий для еды, лекарств и стула. `RecordedTime` хранит `date_only` без времени либо `date_time` с `HH:mm` и UTC-смещением; IANA-зона необязательна и проверяется относительно даты, включая переходы летнего времени. Изменение простой формой сохраняет ранее заданный контекст. `createdAt` не используется для восстановления неизвестного фактического времени.

Новая запись сна хранит отбой и подъём с конкретными датами, подъём относится к выбранному дню. Простая форма считает отбой раньше подъёма частью того же дня, иначе предыдущего дня. `SleepPeriod` позволяет явно задать ночь через API и проверяет хронологию. Неизвестные даты старой ночи сохраняются; вычисленный промежуток не выдаётся за фактический сон.

`DayStatusEntity` уникальна на дату/профиль. Отсутствие строки эквивалентно неподтверждённому дню. `confirmDay` явно подтверждает питание и/или симптомы; итог стула при подтверждённых симптомах — `no_diarrhea`, `diarrhea`, `no_stool`. Противоречие записанным событиям не принимается. Изменение/удаление питания снимает подтверждение питания, стула или самочувствия — симптомов. Просмотр ничего не создаёт. Новые импортированные наблюдения также снимают прежние локальные подтверждения.

Существующая аналитика пока использует прежнее правило предыдущего календарного дня. Интеграция точного времени, полноты и неопределённости состава относится к этапу 8; шкалы состояния и формы полноты — к этапу 6.

## Миграции и перенос

Миграция 4→5 добавляет поля с неизвестными значениями, таблицу компонентов и полноты, количества связей и порядок. Старые ингредиенты, события, UUID, настройки и архив сохраняются; новые подтверждения и источники не создаются. Проверяется цепочка из каждой схемы 1–4 до 5.

[Формат JSON 1–2](backup-format.md) использует строгие поля, адаптер старой версии и транзакционное слияние. Названия не определяют идентичность: автоматическое предложение сопоставления возможно только для уникального в обоих каталогах сочетания вида, типа еды, имени, базовый/вариант, марки и уточнения. Две позиции файла не сопоставляются с одной локальной. Результирующая база проверяется перед завершением транзакции; ошибка откатывает все изменения.
