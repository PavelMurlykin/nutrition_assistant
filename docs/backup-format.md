# Резервные копии Nutrition Assistant: JSON 1–4

Приложение 0.9.0, схема Room 7. Экспорт формирует JSON 4; импорт принимает JSON 1, 2, 3 и 4. Версия JSON независима от Room. Файлы sports_activity_assistant не принимаются. Новый формат не читается прежними версиями приложения, поддерживающими только JSON 1–3.

## Перенос

Вкладка «Данные» сохраняет согласованный снимок всей базы через системный выбор файла Android. Фильтр дневника не ограничивает экспорт; последующие изменения войдут в следующую копию. Дополнительное разрешение накопителя не требуется. Файл — незашифрованный UTF-8 JSON с личными сведениями; приложение не отправляет его на сервер.

Импорт: выбор → проверка → предпросмотр → подтверждение сопоставлений/конфликтов и выбора настроек → «Применить импорт». До применения база не меняется. Применение и повторная проверка результата выполняются одной транзакцией. Ошибка откатывает записи, связи и UUID-сопоставления. Режима очистки/полной замены базы нет.

## Корень

В JSON 4 все семь полей обязательны, неизвестные поля отклоняются:

| Поле | Значение |
| --- | --- |
| `applicationId` | `com.pamurlykin.nutritionassistant` |
| `schemaVersion` | Целое `4` при экспорте; `1`, `2`, `3` или `4` при чтении |
| `appVersion` | Непустая версия создавшего файл приложения |
| `exportedAt` | ISO Instant, время снимка |
| `records` | Массив `{type, publicId, values}` |
| `aliases` | Массив `{sourceId, targetId, type}` |
| `scales` | Полные фиксированные определения шкал: `{metric: {version: 1, values: {code: label}}}` |

`publicId` — канонический UUID в нижнем регистре, уникальный среди всех записей. Числовые ключи SQLite не экспортируются. Живые ссылки внутри `values` содержат UUID и переназначаются при переносе. UUID в историческом дереве остаются исходными: справочник может уже иметь другую версию или быть сопоставлен с другим локальным UUID.

## Поля JSON 4

Все перечисленные поля обязательны, включая nullable-поля с явным `null`. Необозначенные значения — строки. Общие поля события: `user_id`, `date`, `created_at`, `updated_at`. Общие сведения о фактическом времени: nullable `actual_time`, `utc_offset`, `time_zone`, обязательное `time_precision` и nullable `comment`.

| `type` | Поля `values` |
| --- | --- |
| `users` | `breakfast_time`, `lunch_time`, `dinner_time`, `toilet_time`, `wakeup_time`, `bed_time`; булевы `breakfast_enabled`, `lunch_enabled`, `dinner_enabled`, `toilet_enabled`; `created_at`, `updated_at` |
| `catalog` | `kind`, `name`, `normalized_name`, `food_type`, массив строк `ingredients`, булевы `archived`, `favorite`; nullable `category_code`; строки `product_kind`, `brand`, `variant_label`, `composition_state`; nullable `composition_source`, `composition_checked_on`, `comment`; целое `revision`; массив объектов `component_links` |
| `meals` | Общие поля события и времени; `meal_type`, `description` |
| `medicines` | Общие поля события и времени; `name`, nullable `dosage` |
| `stools` | Общие поля события и времени; целое `quality`, nullable целые `scale_version`, `urgency`, `pain`, nullable `quality_label` |
| `health_entries` | Общие поля события и времени; `metric`, `period`, nullable `value_code`, `value_label`, `activity_kind`, `illness_impact`; nullable целые `scale_version`, `day_slot`, `duration_minutes`; массив строк `symptom_codes` |
| `water` | Общие поля события; целое `glasses_count` |
| `sleeps` | Общие поля события; nullable `wakeup_time`, `bed_time`, `quality_description`, `bed_date`, `wakeup_date`, `quality_label`; nullable целые `quality_rating`, `scale_version`, `awakenings` |
| `meal_items` | `meal_id`, `catalog_id`, `name`, `food_type`, массив строк `ingredients`, `kind`, целое `position`; nullable целое `source_revision`, nullable объект `composition_snapshot`, nullable строки `quantity`, `unit`, `comment` |
| `medicine_items` | `medicine_id`, `catalog_id`, `name`, nullable `dosage`; целое `position`; nullable целое `source_revision`, nullable строки `quantity`, `unit`, `comment` |
| `day_status` | Общие поля события; булевы `food_complete`, `symptoms_complete`, nullable `stool_summary` |

- Один локальный профиль `users`; все события ссылаются на него. История объединяется с текущим личным дневником.
- Даты — канонические `YYYY-MM-DD`, годы 0001–9999; время — `HH:mm`. `created_at`/`updated_at` — локальные ISO даты/время создания и изменения, отдельно от фактического времени.
- `time_precision`: `date_only` с тремя nullable-полями времени, равными `null`, либо `date_time` с `actual_time` и `utc_offset`. `time_zone` необязателен; если указан, смещение должно соответствовать IANA-зоне на эту дату, включая переходы летнего времени. Несуществующее локальное время отклоняется.
- `kind`: `product`, `dish`, `medicine`. У блюда `food_type`: `home`, `restaurant`, `unknown`; у остальных пустая строка. `meal_type`: `breakfast`, `lunch`, `dinner`, `snack`; ограничений числа одинаковых типов за день нет.
- `category_code`: один из 15 кодов из [модели данных](data-model.ru.md) либо `null` для неизвестной категории. `product_kind`: `basic` или `variant`; категория и вариант применимы к продуктам.
- `composition_state`: `unknown`, `partial`, `confirmed`. Подтверждение требует непустого источника и даты проверки. Отсутствие ингредиента при неизвестном/частичном составе не подтверждает его отсутствия. `revision` положителен и не больше 2147483647.
- `component_links`: объекты `{product_id, quantity, unit, position}`. Компоненты — только продукты. Блюдо и продукт могут иметь состав, лекарство — нет. Владелец не включает один продукт дважды; порядок уникален, циклы запрещены. `ingredients` каталога сохраняет старую совместимую колонку, обычно пустую.
- `quantity` — строка положительного десятичного числа: до 18 цифр до точки и 6 после. `unit`: `g`, `ml`, `piece`. Оба поля равны `null` либо заданы вместе. Неизвестность не заменяется нулём, пересчёт единиц не выполняется. Отдельный свободный `dosage` лекарства сохраняется.
- `position` — уникальный неотрицательный порядок внутри владельца/приёма. Не зависит от сортировки UUID в JSON.
- `quality`: 1–7, 0 допускается для старого неоценённого стула. `glasses_count`: 0–2147483647. Сон, вода и полнота дня уникальны на профиль/дату.
- `bed_date` и `wakeup_date` задаются вместе либо оба `null` для старой записи. Подъём позже отбоя, дата подъёма равна дате записи. Эти даты обозначают интервал в постели, а не измеренную длительность сна.
- `stool_summary`: `no_diarrhea`, `diarrhea`, `no_stool` при подтверждённых симптомах; иначе `null`. Подтверждение согласуется с записанным стулом: `diarrhea` требует типа 6–7, `no_diarrhea` исключает 6–7, `no_stool` требует отсутствия записей. Неизвестный день не становится нормальным автоматически.
- Название непустое, до 1000 символов. Дозировки и новые комментарии до 1000 символов; импорт сохраняет длинные прежние тексты health_entries.comment и sleeps.quality_description. `normalized_name` соответствует нормализации регистра, пробелов и е/ё.

## Исторический состав

`composition_snapshot` — `{version: 1, root: node}`. Версия дерева независима от версии файла. Узел содержит строго `id`, `name`, `kind`, `revision`, `metadata`, `quantity`, `unit`, `legacy_ingredients`, `components`. Метаданные: `category`, `product_kind`, `brand`, `variant`, `composition`, `source`, `checked_on`, `comment`. Все поля обязательны; nullable-поля сохраняют `null`.

Корень — блюдо или продукт, потомки — продукты. На одном пути UUID не повторяются; в одном узле нет повторных прямых компонентов. Каждая связь сохраняет собственное количество и единицу. Количество корня дерева неизвестно: порция события находится отдельно в `meal_items`. Версия корня совпадает с `source_revision`, имя и вид — с позицией истории; плоские `ingredients` совпадают с развёрнутым списком дерева. Снимок не пересчитывается из текущего справочника и не подменяется при сопоставлении UUID. Повторный ингредиент через разные пути сохраняет пути, но в плоском списке присутствует один раз.

У старой позиции `composition_snapshot` и `source_revision` равны `null`; её исходные плоские ингредиенты остаются прежними. Исторические UUID дерева не обязаны присутствовать среди текущих записей каталога.

## Совместимость JSON 1

Пример [JSON 1](examples/nutrition-backup-v1.json) продолжает читаться строгим адаптером. Сначала проверяются прежние точные поля и ссылки. `product_ids` блюда превращаются в `component_links` с неизвестными количествами. Категория, источник, дата проверки, фактическое время, порции и снимок дерева остаются неизвестными; состав помечается `unknown`, начальная версия каталога — 1. Даты ночи не выдумываются; подтверждений полноты дня не создаётся. Сохраняются все старые UUID, плоские ингредиенты, дозировки и текст.

JSON 2 проверяется по прежним точным полям и на промежуточном шаге дополняется `favorite: false` в каталоге. Избранное не выдумывается по истории.

После импорта экспорт всегда формирует JSON 4. Версии новее 4 отклоняются с предложением обновить приложение. [Пример JSON 2](examples/nutrition-backup-v2.json) содержит снимок рецепта, количество связи и порцию; все примеры синтетические и проверяются тем же Android-декодером.

[Пример JSON 3](examples/nutrition-backup-v3.json) дополнительно содержит булево избранное. `favorite` — предпочтение текущего каталога, оно не меняет версию или исторический состав еды. Флажок восстановления сведений справочника переносит также избранное; по умолчанию локальная отметка сохраняется.

Встроенные продукты и шаблоны новой установки используют постоянные UUID из стабильного ключа. Для прежней записи, выбранной вместо встроенной, в `aliases` хранится соответствие встроенного UUID её UUID. Поэтому переименование и архивирование сохраняются после обновлений и переноса, а повторная инициализация не создаёт исходный продукт заново.

## Проверки и объединение

Лимиты: 16 МиБ UTF-8, суммарно 100 000 записей/сопоставлений/компонентов, включая исторические деревья. Глубина синтаксического JSON — 64, состава — 16 уровней. Развёртывание одного состава и суммарных снимков одного приёма ограничено 10 000 узлами. Дробные JSON-числа не принимаются вместо целых; количества передаются строками.

1. Совпадающие UUID узнаются, одинаковые данные пропускаются. Сравнение события включает все позиции и снимки; изменение одного комментария/состава/дозировки конфликтует со всем событием.
2. При конфликте явно подтверждается сохранение локального события со всеми его позициями. Оно не дополняется позицией из конфликтующей версии файла.
3. Для каталога совпадение по названию предлагается лишь при уникальном в обоих справочниках сочетании вида, типа еды, нормализованного названия, базовый продукт/вариант, марки и уточнения. Неоднозначные позиции остаются отдельными. Сопоставление требует отдельного флажка. Две позиции файла не могут сопоставляться с одной локальной записью.
4. По умолчанию сохраняются локальные сведения каталога. «Восстановить состав и архив справочника из файла» заменяет их выбранной копией, включая новые метаданные, состав, количества и версии; история не переписывается. Для полного восстановления на новой установке включите этот флажок и восстановление настроек.
5. Вода, сон, полнота и дневная оценка одного показателя на одну дату с разными UUID сопоставляются; при различиях сохраняется локальная запись с подтверждением. Импорт новых приёмов пищи снимает прежнее локальное подтверждение питания, новых записей стула/состояния/сна/лекарств — симптомов. Новые импортированные подтверждения дополнительно проверяются по итоговой базе.
6. Настройки профиля по умолчанию локальные. Разрешение Android и операционный журнал уведомлений не переносятся; напоминания пересоздаются из выбранных настроек.
7. Подтверждённые соответствия сохраняются как `backup_aliases` и экспортируются в `aliases`. Повторный импорт узнаётся без дублей. Исторические UUID остаются в снимках без переназначения.
8. SHA-256 локального снимка проверяется внутри транзакции: изменившийся после предпросмотра дневник требует повторной проверки. Итоговая база проверяется целиком, включая граф после сопоставлений. Ошибка откатывает всё.

Предпросмотр показывает общее число объектов и первые 100 подробностей конфликтов/совпадений каждого вида. Повторные ключи JSON, неизвестные поля, неверные типы, ссылки, даты, циклы, версии и несогласованные снимки отклоняются без изменения базы; сообщения не раскрывают содержимое файла.

Предпросмотр и байты экспорта переживают пересоздание экрана в текущем процессе. После завершения процесса файл выбирается заново. Прерванный экспорт может оставить пустой/неполный внешний документ; сохраните новую копию и откройте её в предпросмотре. Атомарная замена документа внешним файловым провайдером не обещается.

Миграции Room 1 → 2 → 3 → 4 → 5 → 6 → 7 проверяются без очистки базы; проверяются также все новые поля, варианты, неизменность истории, повторный импорт, конфликты, устаревший предпросмотр и откат при искусственной ошибке SQLite.

## Шкалы и перенос старого состояния

[Пример JSON 4](examples/nutrition-backup-v4.json) содержит словарь шкал, стресс 0, болезнь unknown, сон без часов и дополнительные оценки стула. Словарь `scales` должен точно совпадать с фиксированными определениями версии 1, включая подписи; неизвестная версия или изменённый смысл отклоняются. Определения и обоснование: [шкалы состояния](health-scales.ru.md).

`health_entries.metric`: stress/activity/wellbeing/illness; value_code — строка. `period=day` требует day_slot=1 и неизвестного точного времени; `moment` требует day_slot=null и допускает несколько записей. Одна дневная оценка показателя на профиль/дату. value_label и scale_version=1 соответствуют коду; null-код разрешён только для прежнего wellbeing/moment с комментарием и без дополнительных оценок. Неизвестность не превращается в 0 или none.

duration_minutes — 1–1440; activity_kind из словаря. Они допустимы только у активности с нагрузкой. illness_impact и уникальные symptom_codes из словаря допустимы только при illness/present. Сон: quality_rating=1–5, label/version согласованы либо все три null; awakenings=0–1000 либо null. Оба часа сна могут быть null, тогда даты также null. Хотя бы качество, комментарий, число пробуждений или оба часа должны быть заданы. Bristol 1–7 имеет версию 1 и точную подпись, legacy 0 — обе null; urgency=0–2 и pain=0–3 либо null.

Адаптеры JSON 1, 2 и 3 сначала проверяют точные прежние поля. feelings превращается в health_entries с тем же UUID, description целиком становится comment, wellbeing/moment без балла/версии/времени. Сопоставления aliases меняют тип таким же образом. Старый sleep сохраняет часы, даты и описание без выдуманного балла. Старый известный Bristol получает подпись версии 1, неизвестный 0 остаётся неизвестным. После переноса экспорт всегда версии 4.
