# Резервные копии Nutrition Assistant: JSON 1

Текущее приложение 0.6.0, схема Room 4; JSON 1 поддерживается начиная с 0.5.0. Версия файла JSON независима от Room. Это формат Nutrition Assistant; файлы sports_activity_assistant не принимаются.

## Пользовательский сценарий

Во вкладке «Данные» экспорт создаёт согласованный снимок всей базы и предлагает сохранить `.json` через системный выбор файла Android. Фильтры дневника не ограничивают копию. Снимок фиксируется перед выбором места, поэтому записи, добавленные позднее, войдут в следующую копию.

Импорт: выбор файла → проверка → предпросмотр → подтверждение сопоставлений/конфликтов и настроек → «Применить импорт». До применения пользовательские данные не меняются. Применение выполняется одной транзакцией; ошибка откатывает все изменения, включая UUID-сопоставления.

Файл — незашифрованный UTF-8 JSON с чувствительными сведениями о здоровье. Экспорт не загружает его на сервер. Хранение и передачу выбирает пользователь. Системный выбор файлов использует [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files); дополнительных разрешений на накопитель приложение не запрашивает.

## Корень

Обязательны все шесть полей; неизвестные поля отклоняются:

| Поле | Смысл |
| --- | --- |
| `applicationId` | Всегда `com.pamurlykin.nutritionassistant` |
| `schemaVersion` | Целое число `1` |
| `appVersion` | Непустая версия приложения, сформировавшего копию |
| `exportedAt` | Время снимка UTC в формате ISO Instant |
| `records` | Массив записей `{type, publicId, values}` |
| `aliases` | Массив ранее подтверждённых сопоставлений `{sourceId, targetId, type}` |

`publicId` — канонический UUID в нижнем регистре, уникальный среди всех записей файла. Числовые ключи SQLite не экспортируются. Ссылки внутри `values` содержат UUID, а не локальные числа. UUID сохраняются при обычном редактировании; новые позиции получают новые UUID.

## Типы записей и поля values

| `type` | Поля `values` |
| --- | --- |
| `users` | `breakfast_time`, `lunch_time`, `dinner_time`, `toilet_time`, `wakeup_time`, `bed_time`; булевы `breakfast_enabled`, `lunch_enabled`, `dinner_enabled`, `toilet_enabled`; `created_at`, `updated_at` |
| `catalog` | `kind`, `name`, `normalized_name`, `food_type`, `ingredients`, `archived`, `product_ids` |
| `meals` | `user_id`, `date`, `meal_type`, `description`, `created_at`, `updated_at` |
| `medicines` | `user_id`, `date`, `name`, nullable `dosage`, `created_at`, `updated_at` |
| `stools` | `user_id`, `date`, целое `quality`, `created_at`, `updated_at` |
| `feelings` | `user_id`, `date`, `description`, `created_at`, `updated_at` |
| `water` | `user_id`, `date`, целое `glasses_count`, `created_at`, `updated_at` |
| `sleeps` | `user_id`, `date`, `wakeup_time`, `bed_time`, nullable `quality_description`, `created_at`, `updated_at` |
| `meal_items` | `meal_id`, `catalog_id`, `name`, `food_type`, `ingredients`, `kind`, целое `position` |
| `medicine_items` | `medicine_id`, `catalog_id`, `name`, nullable `dosage`, целое `position` |

Все перечисленные поля обязательны, в том числе nullable-поля с явным `null`. Остальные значения — строки, кроме специально обозначенных чисел, булевых значений и массивов.

- В файле один локальный профиль `users`. Все события ссылаются на него. При переносе история явно объединяется с текущим личным дневником; импорт нескольких профилей не поддерживается.
- Даты — `YYYY-MM-DD`, годы 0001–9999; время — `HH:mm`. `created_at`/`updated_at` сохраняют существующие локальные ISO даты/время и не подменяют фактическое время события.
- `catalog.kind`: `dish`, `product`, `medicine`. У блюда `food_type`: `home`, `restaurant`, либо `unknown` для исторических записей. У продукта и лекарства — пустая строка.
- `normalized_name` соответствует нормализации названия: крайние/повторные пробелы, регистр и е/ё. Название непустое, до 1000 символов; дозировка — до 1000 символов или `null`.
- `ingredients` — массив строк. У позиции еды он является историческим снимком; `catalog.ingredients` сохраняет совместимую колонку текущей базы, в обычных новых записях пустую.
- `product_ids` — массив UUID продуктов текущего рецепта блюда, без повторов. У продукта/лекарства он пуст. Вложенный состав продуктов появится на отдельном этапе с развитием формата.
- `meal_type`: `breakfast`, `lunch`, `dinner`, `snack`. Снимок `meal_items.kind`: `dish` либо `product`, совместимый с разделом связанной позиции каталога. Прежнее название/состав могут отличаться от текущего справочника.
- `position` — порядок позиции внутри приёма, начиная с нуля. Он уникален в пределах события и сохраняет порядок отображения при переносе независимо от сортировки UUID в JSON.
- `quality`: 1–7 для новых наблюдений, 0 допускается для сохранения старого неоценённого стула. `glasses_count`: 0–2147483647. Для сна и воды допускается одна запись на профиль/дату.
- Сохраняются архивные справочники, дозировки, текст качества сна и самочувствия, старые записи с неизвестным составом. Операционные журналы уведомлений и системные разрешения не переносятся. Напоминания пересоздаются из выбранных настроек; разрешение уведомлений выдаётся Android отдельно.

## Проверка, конфликты и сопоставления

Лимиты чтения и записи — 16 МиБ и 100 000 объектов/компонентов суммарно: записи, сопоставления и элементы списков состава. Максимальная глубина синтаксического JSON — 16. Проверяются строгая кодировка, единственный JSON-документ, отсутствие повторных ключей, точные типы полей, допустимые значения и все ссылки. Дроби вместо целых, неверная дата, отсутствующий родитель, неизвестный тип/поле/версия и повтор UUID отклоняются до применения. Сообщения не показывают фрагменты содержимого файла.

Правила объединения:

1. Совпадающие UUID с теми же данными пропускаются. Сравнение приёма пищи/лекарства включает все дочерние позиции и их снимки: изменение только ингредиента или дозировки также является конфликтом всего события.
2. При различии нужно подтверждение сохранения локальных событий. Событие остаётся целиком прежним вместе со своими позициями; импорт не дополняет его дочерними записями из конфликтующей версии. Для справочника отдельно выбирается правило ниже.
3. До этапа вариантов товаров база допускает уникальное сочетание раздела, типа еды и нормализованного названия. При разных UUID и совпавшем сочетании требуется отдельный флажок «Сопоставить одноимённые позиции…». По умолчанию текущие составы и архив остаются локальными. Флажок «Восстановить состав и архив справочника из файла» явно заменяет текущие сведения сопоставленных продуктов, блюд и лекарств, включая рецепты и названия, сведениями из копии; исторические снимки событий остаются прежними. Для полного восстановления на новой установке включите этот флажок и восстановление настроек. Разные реальные варианты, которые необходимо хранить отдельно, сначала нужно различить названиями; молчаливого слияния нет.
4. Для воды/сна с разными UUID в один день локальная запись сохраняется с явным подтверждением конфликта. Такой выбор запоминается, повторный файл не создаёт дубликаты.
5. Один локальный профиль сопоставляется с текущим. Настройки по умолчанию остаются локальными; для полного восстановления отметьте «Восстановить настройки напоминаний из файла». Системное разрешение уведомлений не меняется.
6. Подтверждённые соответствия сохраняются в `backup_aliases` и входят в следующий экспорт как `aliases`. Они связывают исходный UUID с текущим каноническим UUID и позволяют узнавать повторные импорты после сопоставления. UUID истории сохраняются; UUID сопоставленных справочников/профиля доступны через соответствия. Отсутствующие после удаления цели не экспортируются как действующие соответствия.
7. SHA-256 согласованного локального снимка проверяется в транзакции перед применением. Любое изменение дневника/справочника/настроек за время предпросмотра требует заново выбрать и проверить файл. Ошибка или отмена не очищают базу.

Предпросмотр показывает количество каждого типа, добавляемые и сохраняемые объекты, число конфликтов и сопоставлений. Для больших файлов выводятся первые 100 подробных строк каждого вида с общим числом. Передавать чувствительный файл стоит только после проверки его назначения.

## Миграция и проверки

Миграция Room 3 → 4 добавляет `public_id` к десяти переносимым таблицам, назначает отдельный UUID каждой существующей записи и создаёт уникальные индексы и таблицу явных соответствий. Прежние идентификаторы, данные, связи и снимки не меняются; обновление 1 → 2 → 3 → 4 проверяется Android-тестами. Очистка базы для миграции не используется. Основной импорт — объединение; режима полной замены базы в этой версии нет.

Синтетический [пример JSON 1](examples/nutrition-backup-v1.json) содержит один продукт, одно блюдо и один приём пищи. Это тестовые сведения, не история пользователя. Пример читается тем же декодером в Android-тестах. Проверки также покрывают полный цикл восстановления всех типов, сохранение UUID при редактировании, повторный импорт, настройки, архив, снимки, конфликты, устаревший предпросмотр и откат при искусственной ошибке SQLite.

Предпросмотр и подготовленные байты экспорта находятся в ViewModel и переживают пересоздание экрана в текущем процессе. После завершения процесса нужно выбрать файл заново; незавершённая запись может оставить пустой/неполный файл. Приложение не обещает атомарную замену документа у внешнего файлового провайдера. Сохраните новую копию и проверьте, что она открывается в предпросмотре.
