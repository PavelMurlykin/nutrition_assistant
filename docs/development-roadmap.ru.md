Дата: 16 ноября 2026 года. Основание: видение владельца и проверка текущего кода приложения и резервного копирования в `sports_activity_assistant`.

Это план будущих изменений. Описанные ниже возможности считаются доступными только после реализации и проверки соответствующего этапа.

## Цель и принципы

Помочь человеку вести дневник питания и состояния, видеть полный известный состав съеденного и замечать повторяющиеся связи между продуктами, другими обстоятельствами и эпизодами жидкого стула.

Основной пользовательский путь: выбрать еду из справочника → при необходимости уточнить состав → быстро отметить состояние → увидеть проблемные дни и объяснимые наблюдения → сохранить данные или передать выбранный период для внешнего анализа.

Принципы разработки:

- Основной дневник, справочники, резервные копии и базовая аналитика работают локально, без регистрации и сервера.
- Неизвестный состав, пропущенная запись и подтверждённое отсутствие фактора — разные состояния.
- Справочники упрощают ввод; комментарий дополняет структурированные данные и остаётся необязательным.
- Изменение продукта или рецепта влияет на будущие записи. История хранит состав на момент приёма пищи.
- Приложение показывает наблюдаемые связи и ограничения данных. Числа не выдаются за вероятность диагноза или доказательство непереносимости.

Причины диареи могут включать инфекции, лекарства и пищевые непереносимости. Поэтому состав еды необходимо анализировать вместе с другими записями состояния. Основание: [NIDDK, симптомы и причины диареи](https://www.niddk.nih.gov/health-information/digestive-diseases/diarrhea/symptoms-causes).

## Этап 2. Реализовать резервное копирование JSON

За основу взять подход из `C:\git\sports_activity_assistant\docs\backup-format.md` и `data/backup`: выбор файла, версия формата, независимые идентификаторы, проверка, предпросмотр, явное применение и транзакция. Данные о тренировках и их формат не переносятся в Nutrition Assistant.

Работы:

- Добавить раздел «Данные»: «Экспорт резервной копии» и «Импорт из JSON». Файлы выбираются и сохраняются через системный диалог Android.
- Ввести собственный формат с `applicationId`, `schemaVersion`, `appVersion`, `exportedAt` и идентификаторами объектов. Версия JSON независима от версии Room.
- Добавить UUID минимальной недеструктивной миграцией для переносимых объектов до крупной перестройки модели. Один объект сохраняет UUID при следующих экспортах.
- Сохранять весь пользовательский дневник, справочники, архивные позиции, исторические снимки, комментарии и пользовательские настройки. Фильтр текущего экрана не ограничивает резервную копию.
- Не восстанавливать технические журналы отправленных уведомлений как пользовательские события. Напоминания пересоздаются из восстановленных настроек, с учётом разрешения Android.
- Перед записью проверять версию, типы, диапазоны, даты, уникальность UUID, ссылки и ограничения размера. Повреждённый или чужой файл не меняет базу.
- Принять исходные лимиты референса — 16 МиБ и 100 000 объектов; проверить пригодность на многолетнем дневнике. Для вложенного состава дополнительно ограничить глубину и размер развёртывания.
- Показывать предпросмотр: объекты к добавлению, совпадения, конфликты, изменения настроек и ошибки. Отмена не изменяет данные.
- Основной режим — объединение: тот же UUID и те же данные пропускаются; различия показываются как конфликт с сохранением локальной записи по умолчанию. По одному названию продукты автоматически не объединяются.
- Восстановление на чистой установке возвращает полный дневник. Полная замена существующей базы, если понадобится, проектируется отдельным явно обозначенным режимом с предварительным сохранением текущей базы.
- Применять импорт одной транзакцией; проверять актуальность предпросмотра перед применением. Ошибка записи откатывает всю операцию.
- Сообщать, что JSON содержит чувствительные сведения и не зашифрован. Сохранение и передачу файла запускает пользователь; содержимое не попадает в диагностические журналы.

Критерии готовности:

- Экспорт → чистая установка → импорт сохраняет значения, связи, архив и настройки.
- Повторный импорт того же файла не создаёт дубликаты.
- Повреждение, неподдерживаемая версия, конфликт и отмена не приводят к молчаливой потере истории.
- Формат документирован; есть синтетический пример и проверки восстановления.

## Этап 4. Расширить модель данных и сохранить историю

Целевая структура:

| Сущность | Основные сведения и связи |
| --- | --- |
| Категория продукта | Стабильный код, название, порядок; сначала одна основная категория у продукта |
| Продукт | UUID, название, категория, базовый продукт/конкретный вариант, марка при наличии, комментарий, архив |
| Состав продукта | Продукт → продукт-компонент, порядок, количество и единица при наличии; состав может быть вложенным |
| Сведения о составе | Неизвестен / частичный / подтверждён по источнику; источник, дата проверки, версия |
| Блюдо | Название, домашнее/ресторанное, продукты рецепта, количество при наличии, комментарий, архив |
| Приём пищи | Дата, фактическое время при наличии, тип, позиции «блюдо или продукт», порции, комментарий |
| Историческая позиция еды | Снимок названия, состава, версии, количества, источника и степени определённости на момент записи |
| Приём лекарства | Время при наличии, позиции справочника, отдельные дозировки и единицы, комментарий |
| Состояние | Версионируемые коды шкал, время/период наблюдения, комментарий; неизвестность отдельно от нулевого значения |
| Полнота дневника | Явное подтверждение пользователем учёта питания и симптомов за день; неполный день по умолчанию |

Правила реализации:

- Состав продукта образует ориентированный граф без циклов. Запрещены прямое и косвенное включение в себя; проверка действует и в редакторе, и при импорте.
- Базовый «говяжий фарш» и «говяжий фарш марки X с чесноком» — разные позиции. Нормализация названия используется для поиска и подсказки совпадений, идентичность определяется UUID.
- Пересмотреть текущий уникальный ключ по виду, типу еды и названию: он не должен блокировать реальные варианты товаров с одинаковым названием.
- Путь состава сохраняется: «котлета → покупной фарш → чеснок». Повторяющийся ингредиент не превращается в несколько независимых наблюдений; количество суммируется только при известных совместимых единицах.
- При необходимости добавить отдельные метки наблюдаемых веществ, например лактозы. Их наличие и источник подтверждения хранятся явно: название «хлеб» само по себе не подтверждает лактозу, отсутствие ингредиента в неполном составе не подтверждает его отсутствия.
- Доступные количества вводятся в граммах, миллилитрах или штуках. Они необязательны; неизвестная масса не подменяется нулём, штуки не переводятся в граммы без данных.
- Фактическое время приёма пищи, лекарства и стула отделяется от времени создания записи. Хранятся локальная дата, часовой пояс/смещение при наличии и точность: только дата или дата и время.
- Старые записи остаются с неизвестным фактическим временем. `createdAt` не используется как время еды или симптома без подтверждения пользователя.
- Время сна относится к конкретной ночи с переходом даты; длительность пребывания в постели не выдаётся автоматически за фактическую длительность сна.
- Снять ограничение «один завтрак/обед/ужин за день», если оно мешает фактическому дневнику: тип классифицирует событие, а не определяет его уникальность.
- При редактировании справочника старые снимки не меняются. Обновление состава отдельного прошлого приёма пищи выполняется только как явное редактирование этой записи.
- Старый текст и плоские ингредиенты сохраняются без выдуманного вложенного состава, шкал и источников. Неоднозначность отмечается явно.
- Миграции не используют очистку базы; экспорт и импорт поддерживают новые поля в том же этапе. Старые резервные копии читаются через адаптеры, неизвестные новые версии отклоняются с понятным сообщением.

Критерий готовности: миграция всех существующих версий сохраняет историю; циклы отклоняются; изменение рецепта не меняет прошлые приёмы; новая база полностью восстанавливается из JSON.

## Этап 5. Наполнить каталог и упростить ввод питания

Работы:

- Подготовить стартовый каталог примерно из 80–120 распространённых базовых продуктов. Точное наполнение проверить на повседневных сценариях, без привязки к магазинам.
- Категории: крупы и зерновые, мука и хлеб, овощи и зелень, фрукты и ягоды, мясо и птица, фарш и полуфабрикаты, рыба и морепродукты, яйца, молочные продукты и альтернативы, бобовые, орехи и семена, масла, специи и соусы, напитки, прочее.
- Обязательно включить гречку, рис, яйца, говядину, свинину, курицу, индейку и соответствующие виды фарша. «Фарш без добавок» и готовый товар с добавками различаются.
- Состав универсального магазинного хлеба, пельменей или фарша не объявлять известным. Пример рецепта обозначать как шаблон; конкретный покупной вариант заполняется по упаковке или другому указанному источнику.
- Обновлять встроенный каталог по стабильным ключам: добавлять новые позиции, не перезаписывая пользовательские исправления и архивирование. Сопоставление со старым каталогом показывать при неоднозначности.
- Добавить фильтр категории, поиск по названию и при необходимости компоненту, избранное и недавние позиции.
- Из редактора блюда позволить создать продукт, уточнить его состав и сразу включить в рецепт.
- Сохранить единый выбор блюд и продуктов в приёме пищи; предусмотреть повтор недавнего приёма с проверкой состава и порции.
- Для лекарств сохранить отдельный справочник и дозировки. Полный медицинский каталог и рекомендации по приёму в этот этап не входят.

Критерии готовности на примерах:

- «Пельмени» добавляются одним продуктом; их ингредиенты доступны для просмотра и анализа.
- «Котлета говяжья + пюре + огурец» сохраняется одним приёмом пищи из двух блюд и продукта.
- Чеснок находится внутри покупного фарша и виден в составе котлеты, приготовленной из него.
- Два варианта хлеба с разным составом сохраняются раздельно; неизвестный состав заметен.

## Этап 6. Ввести фиксированные шкалы состояния

Для повседневного ввода предлагаются собственные короткие шкалы приложения. Они предназначены для последовательного личного наблюдения; медицинская валидность им не приписывается. Числовые коды, подписи и версия шкалы сохраняются в данных.

| Показатель | Предлагаемый ввод | Период и дополнения |
| --- | --- | --- |
| Стул | Бристольская шкала 1–7 | Отдельное событие с временем; необязательные срочность позыва, боль и комментарий |
| Качество сна | 1 — очень плохое, 2 — плохое, 3 — среднее, 4 — хорошее, 5 — очень хорошее | За завершившуюся ночь; время отбоя/подъёма, пробуждения по желанию, комментарий |
| Стресс | 0 — отсутствовал, 1 — слабый, 2 — умеренный, 3 — сильный, 4 — очень сильный | Общая оценка за день; при желании отдельное событие со временем и комментарием |
| Физическая активность | Не было / лёгкая / умеренная / высокая | Время или продолжительность при наличии, вид активности и комментарий; несколько нагрузок допустимы |
| Общее самочувствие | 1 — очень плохое, 2 — плохое, 3 — среднее, 4 — хорошее, 5 — очень хорошее | За день либо отдельный момент; время и комментарий |
| Болезнь | Нет признаков / есть признаки / не знаю | При наличии — лёгкое / умеренное / тяжёлое влияние на обычные дела; категории симптомов и комментарий |
| Лекарства | Выбор из справочника | Фактический приём, дозировка, единица, время и комментарий |

У каждого показателя есть состояние «не заполнено». Оно отличается от «стресса не было», «активности не было», «признаков болезни нет» и «стула не было». Для категориальных выборов питания, состава и лекарств также предусматривается необязательный комментарий на соответствующем уровне записи.

Для активности дать короткие подсказки интенсивности. Например, при умеренной нагрузке человек обычно может разговаривать, но ему трудно петь; при высокой — произнести длинную фразу без паузы. Это ориентир самооценки интенсивности, а не готовая шкала дневной активности. Основание: [CDC, измерение интенсивности активности](https://www.cdc.gov/physical-activity-basics/measuring/index.html).

Проверенные готовые инструменты для возможного отдельного опроса:

- **WHO-5** оценивает психическое благополучие за последние две недели. Он не заменяет ежедневную оценку физического самочувствия. У опубликованного материала есть ограничения некоммерческой лицензии, поэтому применимость к выпуску приложения нужно проверить. Источник: [WHO, WHO-5](https://www.who.int/publications/m/item/who-ucn-msd-mhe-2024.01).
- **PSQI** относится к сну за прошедший месяц. Перед включением необходимо проверить разрешение на использование, электронный формат и перевод; коммерческое применение требует отдельного рассмотрения условий. Источники: [University of Pittsburgh, условия использования](https://www.sleep.pitt.edu/research/measures-and-study-instruments), [оригинальный опросник PSQI](https://www.sleep.pitt.edu/sites/default/files/assets/Instrument%20Materials/PSQI-Instrument.pdf).
- **PSS-10** в исходной форме спрашивает о последнем месяце. CMU направляет запросы разрешений через MAPI Research Trust. Для ежедневного дневника предлагается самостоятельная короткая оценка без названия PSS. Источники: [исходная форма PSS-10](https://www.cmu.edu/dietrich/psychology/stress-immunity-disease-lab/scales/html/pss.html), [условия использования](https://www.cmu.edu/dietrich/psychology/stress-immunity-disease-lab/scales/index.html).

Работы:

- Добавить компактную форму заполнения дня; комментарии раскрываются по желанию.
- Хранить болезнь как наблюдение пользователя, не требуя самостоятельного выбора диагноза. По желанию можно отдельно записать уже установленный врачом диагноз.
- Для нескольких оценок за день показывать события и явно подписанную сводку. Разные шкалы не суммируются в общий «индекс здоровья».
- Сохранить воду и существующие сведения о сне. Старый свободный текст переносится в комментарий, числовой балл автоматически не угадывается.
- Добавить подтверждение полноты питания и записей симптомов за день. Наличие одной записи не делает весь день полностью заполненным.

Критерий готовности: все показатели заполняются выбором понятного значения без обязательного текста; пропуски не превращаются в норму; комментарии сохраняются при редактировании и переносе JSON. Целевой ориентир быстрого заполнения обычного состояния за день — около минуты, проверяемый на пользователе.

## Этап 7. Отмечать проблемные дни в календаре

Работы:

- Показывать красную отметку дня, если зарегистрирован хотя бы один эпизод типа 6 или 7. В легенде назвать её «Жидкий стул, тип 6–7», а не медицинским диагнозом.
- Отдельно показывать число таких эпизодов. Тип 5 сохраняет собственную категорию и сам по себе не включает красную отметку.
- Дополнить цвет символом и текстом для доступности; сохранить различимость сегодняшнего и выбранного дня.
- Различать неполный дневник, подтверждённый день без жидкого стула и день с эпизодом. Отсутствие записи не означает здоровый день.
- По нажатию открывать временную последовательность еды, лекарств и состояния; добавить фильтр проблемных дней и сводку за месяц.
- После изменения или удаления события отметка сразу пересчитывается.

Такое правило подсветки — продуктовая договорённость для поиска эпизодов. Клиническое описание диареи учитывает также частоту и изменение относительно обычного состояния; одного номера шкалы недостаточно для диагноза. Основание: [NIDDK, симптомы диареи](https://www.niddk.nih.gov/health-information/digestive-diseases/diarrhea/symptoms-causes).

Критерий готовности: корректно отображаются смешанный день с разными типами стула, тип 5, несколько эпизодов, пустой день, подтверждённое отсутствие симптома, удаление последнего эпизода и переход между месяцами.

## Этап 8. Расширить объяснимую аналитику

Внедрять последовательно: сначала качественная сводка и прозрачные сравнения, затем — более сложные методы, если накопленные данные их оправдывают.

Работы:

- Показывать покрытие дневника: период, полноту питания и симптомов, неизвестный состав, записи без времени. При недостатке наблюдений явно писать «Недостаточно данных».
- Строить временную последовательность до эпизода. Исследовать окна 0–6, 6–24 и 24–48 часов как настраиваемые аналитические предположения; это не универсальные медицинские сроки реакции.
- Для старых записей без времени оставить отдельный анализ по календарным дням с соответствующей подписью. В точные часовые окна они не попадают с выдуманным временем.
- Учитывать продукты, вложенные ингредиенты, блюда, порции при наличии, лекарства и дозировки, сон, стресс, активность, самочувствие и болезнь.
- Для дневной оценки, внесённой после симптома и не имеющей точного времени, не утверждать, что фактор предшествовал эпизоду. Сон сопоставлять с конкретной завершившейся ночью.
- Сравнивать наблюдения с фактором и без него только при достаточной полноте данных. Отсутствие продукта в неполном дневнике не трактовать как отсутствие воздействия.
- Показывать числа и знаменатели: например, «из 8 пригодных дней с продуктом в 5 был отмечен жидкий стул; из 10 дней без него — в 2». Указывать правило сопоставления и период.
- Различать число эпизодов и число дней. Несколько посещений туалета за день не превращаются в независимые подтверждения одного пищевого фактора.
- Заранее определить минимальные размеры групп и правила неопределённости на синтетических сценариях. Малые группы не получают уверенный рейтинг.
- Выделять совместно встречающиеся факторы. Если чеснок всегда отмечен вместе с одним фаршем, объяснять, что дневник пока не позволяет разделить их влияние.
- Отдельно показывать дни болезни и изменения лекарств как возможные смешивающие факторы. Учитывать, что лекарство могло быть принято уже после симптома.
- Категории продуктов использовать для навигации и групповой сводки; одинаковая категория не означает одинаковую переносимость.
- Предусмотреть профиль «что хочу отслеживать»: подозреваемые продукты/компоненты, источник предположения пользователя, история наблюдений. Не присваивать автоматически подтверждённую непереносимость.
- В версии без языковой модели комментарии показывать рядом с наблюдениями, сохраняя их смысл. Автоматический смысловой разбор текста — отдельная функция этапа 11.

Пример карточки: «Чеснок встречался перед частью эпизодов. Источник: котлета → фарш марки X → чеснок. Данных пока мало; фарш и чеснок встречались вместе. Это наблюдение не устанавливает причину».

Критерии готовности:

- Проверены повторяющаяся связь, отсутствие связи, малый объём, совместные факторы, пропуски, неизвестный состав, смена рецепта, лекарство после симптома и границы суток.
- Будущие события не участвуют в объяснении прошлого эпизода.
- Из каждого наблюдения доступны исходные записи и правило расчёта; приложение не выдаёт «вероятность непереносимости 87%» без обоснованной модели.

## Этап 9. Выгружать данные для внешней нейросети

Это отдельная задача от резервного копирования: backup сохраняет всё для восстановления, аналитический пакет представляет выбранные данные для чтения и исследования.

Работы:

- Добавить выбор периода и состава выгрузки: питание, раскрытый исторический состав, лекарства, шкалы, комментарии, полнота дневника и наблюдения аналитики при наличии.
- Создавать структурированный JSON и читаемый Markdown/текст с хронологией, словарём шкал, единицами, часовыми поясами, правилами пропусков и неизвестного состава.
- Сохранять ссылки-идентификаторы исходных событий, чтобы вывод можно было сопоставить с дневником.
- Предоставить режим удаления имени/названий магазинов и исключения комментариев. Предупредить, что свободный текст может содержать личные сведения; не обещать полную анонимность автоматически.
- Добавить редактируемый запрос для внешней модели: анализировать связи, разделять факты и гипотезы, учитывать лекарства и болезнь, перечислять ограничения и ссылаться на события.
- Передавать файл только по явному действию пользователя через сохранение или системное меню. Отправку в конкретный сервис и облачную интеграцию в этот этап не включать.
- Включённые комментарии трактовать как данные дневника, а не инструкции для анализа.

Критерий готовности: за выбранный период экспортированы все отмеченные типы событий и комментарии; значения и состав совпадают с дневником; выключенные поля отсутствуют; пакет читается без знания внутренней схемы Room.

## Этап 10. Проверить и добавить ссылки на магазины

Сначала подготовить конкретные варианты интерфейса и правовую записку для предполагаемых рынков распространения:

1. Пользователь вручную сохраняет URL на упаковку или товар.
2. Приложение показывает название магазина и открывает карточку товара.
3. Приложение само загружает состав, фотографии и цены.
4. Присутствуют партнёрские ссылки, продвижение или логотипы.

Эти варианты проверяются отдельно. Одного факта упоминания компании недостаточно для универсального вывода о допустимости конкретного оформления. Для РФ исходная проверка должна учитывать исключительные права на товарный знак и риск смешения; [статья 1484 ГК РФ](https://www.consultant.ru/document/cons_doc_LAW_64629/7d076153e9adb1b3534c04eb371e2f7c6df713f8/) не является общим разрешением на любое использование названия в приложении. Это предварительное определение вопросов для проверки, а не юридическое заключение.

Работы:

- Проверить названия и логотипы, отсутствие впечатления официального партнёрства, условия сайтов/API и права на фотографии и описания. Для партнёрства и рекламы отдельно проверить применимые требования.
- До выбора конкретных магазинов не обещать автоматическую загрузку состава или разрешённость использования их брендинга.
- После проверки начать с ручного HTTPS URL в карточке продукта и открытия во внешнем браузере. Это проектный вариант с меньшим объёмом интеграции, а не гарантия юридической допустимости.
- Хранить несколько ссылок, название источника и дату проверки. Состав фиксировать отдельно: страница товара может измениться.
- Не передавать магазину дневник и не добавлять в URL данные состояния пользователя.
- Ручная ссылка и внешний браузер не требуют превращения основного дневника в онлайн-приложение. Автоматическую загрузку рассматривать отдельно.

Критерий готовности: описаны применимые ограничения для выбранного варианта и рынков; интерфейс им соответствует; ссылки не меняют исторический состав продукта.

## Этап 11. Исследовать модель на телефоне

Этап начинается с прототипа и заканчивается решением о целесообразности. Наличие небольшой модели само по себе не гарантирует полного или достоверного медицинского анализа.

Работы:

- Выбрать 1–2 задачи: выделение упомянутых обстоятельств из комментариев и понятное изложение уже рассчитанных наблюдений.
- Подготовить русскоязычные синтетические примеры: отрицания, неопределённость, несколько событий, лекарства после симптома, противоречия и неизвестный состав.
- До выбора модели определить поддерживаемые телефоны и критерии качества, памяти, размера, скорости и энергопотребления. Проверить лицензию модели и среды выполнения.
- Проверить полностью локальную обработку и доступность функции без сети после установки необходимых компонентов. Источник и способ установки модели выбрать отдельно с учётом размера приложения и разрешений.
- Любое извлечённое из комментария значение показывать как предложение для подтверждения. Не переписывать дневник и не менять численные расчёты на основании свободного ответа модели.
- Показывать источники выводов, уметь отвечать «Недостаточно данных», сохранять версию модели и возможность отключить функцию.
- Сравнить результат с обычной аналитикой и шаблонным объяснением. Если прирост пользы невелик либо качество на целевых устройствах недостаточно, оставить базовую аналитику и внешнюю выгрузку.

Критерий перехода к выпуску: подтверждена польза на тестовых сценариях и выбранных устройствах; соблюдены заранее заданные ограничения ресурсов; нет вымышленных событий и скрытого изменения пользовательских данных.

## Проверки и условия выпуска

Обязательные проверки для соответствующих этапов:

- Сохранность: миграции всех существующих схем, снимки состава, архивирование и полный цикл резервного копирования.
- Предметная модель: прямой и косвенный цикл состава, неоднозначные названия, базовые и покупные варианты, количества, неполный состав и обновление встроенного каталога.
- Дневник: переход через полночь, неизвестное время старой записи, шкалы и комментарии, несколько событий одного типа, полнота дня.
- Аналитика: пропуски, малые группы, совместные факторы, будущие записи и различие дней/эпизодов.
- Интерфейс: основной путь, все окна, светлая/тёмная тема, клавиатура, большой шрифт и минимальная поддерживаемая версия Android.
- Документация: при реализации каждого этапа обновлять русское и английское руководства, описание формата JSON и ограничения только до реально доступного поведения.

Перед выпуском этапов с изменениями кода выполнять подходящие модульные и Android-тесты, сборку и lint. Команды проекта описаны в [README](../README.md). Для этого документа сборка не требуется: код приложения не изменяется.

Рекомендуемые выпуски:

- **Выпуск A — надёжное ведение дневника:** этапы 1–7. Есть резервные копии, единый интерфейс, вложенный состав, категории, шкалы, комментарии и красные отметки.
- **Выпуск B — анализ накопленной истории:** этапы 8–9. Пользователь понимает, на каких записях основаны наблюдения, и может выгрузить выбранный период.
- **Выпуск C — дополнительные возможности:** этап 10 после правовой проверки; этап 11 только после успешного прототипа. Эти функции не блокируют выпуски A и B.

Оценку трудозатрат и календарные сроки назначить после этапа 1 и оценки объёма миграций. Первое практическое действие — согласовать правила данных на примерах и реализовать проверяемое восстановление JSON до расширения базы.
